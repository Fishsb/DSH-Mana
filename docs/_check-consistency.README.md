# 一致性检查器使用说明

> 本目录的 `_check-consistency.mjs` 是对 `mana-rollout-plan.md` 的**确定性穷尽检查器**。
> 它的存在理由：**人工逐轮抽查总有遗漏**（本册经历 5 轮人工审查，每轮都还能查出新问题）。
> 把检查固化成脚本后，「是否一致」从**主观判断**变成**可重复的机器判据**。

## 一、怎么用

```powershell
cd D:\Mana\docs
node _check-consistency.mjs
```

- **退出码 0** = 无 FAIL（通过）；**退出码 1** = 有 FAIL
- 输出三类：`PASS`（通过项）/ `WARN`（已知可接受）/ `✗ FAIL`（必修）

**跨平台（2026-09-24 修）**：脚本不再硬编码 `D:/Mana/docs/...`，改为**按脚本自身所在目录**定位两册，Windows 与 WSL 均可直跑：

```bash
cd /mnt/d/Mana/docs && node _check-consistency.mjs     # WSL
node _check-consistency.mjs <本册> <方案原件>            # argv 覆盖（可指向副本做变异测试）
```

> ⚠ **别用管道取退出码**：`node _check-consistency.mjs | tail` 的 `$?` 是 `tail` 的退出码，
> 脚本崩溃也会显示 0。要判真值必须 `node ... >out 2>err; echo $?`。

## 二、它检查什么（19 组 / 20 个检查项）

> 注：脚本实跑输出 C1–C19 共 20 个检查项（C9 出两条）。本表早前只记到 C15，与脚本漂移，已于 2026-09-24 补齐。

| 组 | 检查内容 | 判据 |
|---|---|---|
| **C1** | 判据行结构 | ID 唯一；**恰好 5 列**；四要素（判据/检查方式/阈值/退回动作）非空且非「—」；每阶段编号连续无跳号 |
| **C2** | 章节结构 | 七阶段两节齐备；阶段号连续；**小节编号升序无乱序**；小节前缀与阶段号一致；顶级章节号递增唯一 |
| **C3** | 判据 ID 引用完整性 | 被引用的 ID 必须已定义（反向：无引用的仅 WARN） |
| **C4** | 行号引用溯源 | 抽取全部「行NNN」，按**就近 §** 回原方案核对章节归属 |
| **C5** | 数字分档纪律 | B 档浮动值（20.92/35.877/1037/5785 等 12 个）**不得出现在任意判据的阈值列** |
| **C6** | 不可判定表述 | 禁止「性能良好/响应及时/基本可用」等（自动排除批判性引用） |
| **C7** | 表格完整性 | 全表列数一致；**按 GFM 规范处理 `\|` 转义**（否则误报） |
| **C8** | 章节撞号 | 方案独有章节号（§11–§19）无「方案」前缀时告警；已声明语境（表头含「方案声称/原方案」）与同行已有「方案 §」的自动豁免 |
| **C9** | G 清单完整性 | G1–G15 定义齐备；归属表每条标状态（✅/⏳） |
| **C10** | 原方案行数 | 交叉核对「1241 行」声称 |
| **C11** | 术语一致性 | 同概念不得有多重写法（fail-closed / allowExtension / node:test 等 6 对） |
| **C12** | 裸行号 | 引用方案行号必须带 §（排除源码行号、grep 结果、同行延续引用） |
| **C13** | 标记配对 | 反引号/粗体奇偶校验（**排除代码围栏**） |
| **C14** | 阈值列纯净 | 阈值列不得为空、不得含不可判定词 |
| **C15** | 反证判据齐备 | 每个阶段段至少一段「反证判据」 |
| **C16** | 本册内部 § 引用可解析 | 指向本册的小节/顶级节号必须真实存在（收录 23 个小节号） |
| **C17** | 关键事实数字一致 | 同一事实（判据总数 53 / 批次数 18）多处出现必须同值 |
| **C18** | 编号体系齐备 | C15 / G15 / W4 / B18 的编号定义齐备且引用无悬空 |
| **C19** | vec0 语义落点 | §2.2 四条 vec0 语义均在本册有处置落点 |

## 三、这个检查器自己验证过吗

**验证过，方法 = 变异测试**（mutation testing）：故意往文档注入 5 类缺陷，看检查器能否报红。

| 注入的缺陷 | 是否检出 | 报红内容（2026-09-24 复跑实测） |
|---|---|---|
| 删掉某判据的「退回动作」（改 `—`） | ✅ 检出 | `✗ [C1] 四要素缺项（含「—」）: A0-1` |
| 判据编号跳号（A0-2 → A0-9） | ✅ 检出 | `✗ [C1] 判据 ID 重复: A0-9` + `✗ [C1] 阶段 0 编号跳号，缺: 2`（3 条） |
| 小节乱序（0.2 → 0.5） | ✅ 检出 | `✗ [C2] 阶段 0 缺「验收方案」节` + `✗ [C16] L210 指向本册 §0.2，但本册无此小节`（4 条） |
| B 档浮动值混入阈值列（20.92） | ✅ 检出 | `✗ [C5] A0-1 阈值列含 B 档浮动值 20.92` |
| 表格多加一列 | ✅ 检出 | `✗ [C1] 列数≠5 的判据行: A0-1(L336,7列)`（13 条） |

**5/5 全部检出** ⇒ 检查器**有真实检测能力**，不是恒绿摆设。
（变异在 `/tmp` 副本上进行，**源文件全程未被触碰**；源册 sha256 复核见下。）

另验证**确定性**：连续运行 3 次，输出哈希**完全一致**（2026-09-24 复测：`a8d41a02…`）。

> 认定口径（2026-09-24 加）：**「5/5 检出」以「有 `✗ [Cn]` 行且 exit=1」为准**。
> 只看 exit code 会被管道吞掉（Node 进程用管道时常以 0 退出，见 §一 注），
> 必须同时数 `✗ ` 行数——本篇上一版就只写了 exit 而漏记行数，属可观测性缺陷。

## 四、边界（检查器不做什么）

- **只读**：不修改 `mana-rollout-plan.md`，不写任何文件（输出仅到 stdout）
- **不联网、不装包**：仅用 node 内置 `node:fs`
- **不检查内容对错**：它查的是**形式一致性**（结构/编号/引用/分档）；「判据内容是否真的可执行」需人工或干跑验证

## 五、已知 WARN（可接受，不必修）

- **C3 的「仅定义处出现」**：约 18 条判据只在定义表里出现、无正文回引。这是**正常**——判据按阶段顺序取用，无需每处回引；强行回引是为一致性而一致性。

## 六、一个方法论提醒（为什么之前"查一次有一次"）

前 5 轮人工审查的覆盖是**抽样式**的：每轮换一个角度、抽一部分条目。
⇒ 每轮都能查出新问题，但**无法证明「已查完」**。

改成脚本后：
- 覆盖是**穷尽**的（全部 53 条判据 × 19 个维度）
- 结果是**可复现**的（三次运行哈希一致）
- 能力是**可证伪**的（变异测试能报红，且记报红行数）

⇒ 「完全无误」这个判据，从**"我检查过了"**变成了**"脚本全绿且脚本本身经变异验证"**。

**补一条（2026-09-24 实测教训）**：检查器只扫 `mana-rollout-plan.md`，
**不扫自己的说明档**。于是「README 写 15 组、脚本实跑 19 组」的漂移没人发现——
防漂移工具自身漂移，正是它要防的那类失败。**说明档的覆盖边界必须写进说明档**。
