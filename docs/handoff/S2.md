## 2 · 形态映射决策（本轮的核心取舍，逐条给理由）

### 决策 A：`choice`/`score` **不是降级** ⇒ `degraded:false`、`value:'unknown'`、`probability:null`

理由（三条，互相独立）：
1. **契约把 `degraded` 定义为"判定链路降级"**（`domain.ts`：「`degraded` 为真时表示判定链路降级」）。一次 HTTP 200、答案完整、带 `confidence=1` 的 choice 判定**恰恰是链路完全健康的形态**；把它标成降级会让真正的降级（超时/401）被稀释。
2. 反方向同样错：把它压成 `value:'yes'/'no'` 是**编造**（choice 三分类没有 yes/no 语义）。
3. `unknown` 是契约**已有的合法取值**，且契约明令「判定失败 ⇒ `'unknown'`，**不得默认成 'no'`」—— 我据同一精神使用它，**不新增契约取值**。

### 决策 B：`choice`/`score` 的真实取值**不丢**，放在适配层自己的返回类型里

`JevJudgeOutcome`（适配层的类型，**不是契约**）新增**可选**字段 `answers`（`Record<问题键, 归一后的答案>`），choice 落 `choice`/`probabilities`/`confidence`，score 落 `score`/`legend`/`probabilities`/`confidence`。
- 为什么放适配层返回类型而不是 `reason`：`reason` 的契约语义是「降级原因」，把正常数据塞进去 = 下游一定会读错。
- 为什么是**可选**：Ollama 通道不产出它 ⇒ 旧调用方零影响（22 + 11 条旧判据一行不红）。
- 不丢的**可断言证据**：离线判据断言 `answers.v.choice === 'bug'` 且 `probabilities` 逐项保留。

### 决策 C：多问**全保留** + **显式声明主问题**

`questions` 可多个 ⇒ 返回 `answers` 全量保留；契约单值面取 `primaryQuestion`（缺省 `'v'`，可配）。
- **拒绝静默压扁**：若 `primaryQuestion` 缺省键不在返回的 `answers` 里，**不**偷偷挑第一个，而是显式降级 `systemone-primary-missing: <可用键列表>`。
- ⚠ **我不掩盖一个事实**：多问时"其余答案落在适配层字段里"这一层，**只有适配层自己看得到**；下一个消费方若直接把结果塞进 `jev_log`（三列宽的契约），多答仍会被压成一行。⇒ 本轮**不**把多问接到 `jev_log`，多问能力只在探测脚本与离线判据里演示。

### 决策 D：`probability` 用 `noul` 值，判 `value` 用**与旧通道同一条门限**

`threshold` 语义保持不变（`p >= threshold ⇒ 'yes'`），旧调用方与旧判据口径一致。

## 8 · 已知局限（如实列，不当"已解决"）

1. **多问的落库面仍是一行**：`answers` 全量保留在适配层返回值里，但 `jev_log` 只有 `result_value/probability` 三列宽 ⇒ 一次多问在库里仍被压成**主问题一行**。本轮**不**扩表（表结构属 core 边界），故多问能力的可用性只在探测脚本与判据里成立；接消费方时要显式做，别以为库里已有。
2. **`score` 类型本轮只做映射与判据，无真机锚点**：`score=` 的取值语义（索引 + legend）按实测形态实现，但**未**设"某个 state 必须得几分"的锚点（那需要业务口径，本席无权定）。
3. **真通道判据的凭据面依赖用户机器上的 `~/jev/.env`**：换机器时须同时带上该文件或注入环境变量，否则判据会**显式红**（这是设计，不是缺陷）。
4. **`writeJevLog` 的 `cost_usd` 只有真通道会填**；本地 Ollama 仍写 `null`（**不得用 0 冒充**）。
