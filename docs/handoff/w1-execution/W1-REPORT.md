## 三、我在本波亲手修的东西

### 3.1 core 写入口的静默毁数据缺陷（★ 我修的，非任何席）

**位置**：packages/core/src/index.ts:547
**缺陷**：`INSERT OR REPLACE` 只列 5 列 ⇒ 同 id 重写时**未列出的列全部被重置**（REPLACE = DELETE+INSERT）。

**为什么它比派单描述的严重**：`vector` BLOB 被打空 ⇒ **向量检索的数据源没了，而读侧只看到「没命中」——与「库本来就空」同形**。这正是本仓最忌的「会掩盖其他问题」。

**修法**：改 UPSERT（`ON CONFLICT(id) DO UPDATE SET` 只更新真正提供的列），`created_at` 不再被篡改。

**判据**：packages/core/tests/write-memory-item-upsert.test.mjs 3 例（9 列逐列断言）。
**负向对拍**：变异回 `INSERT OR REPLACE` ⇒ **必红**；恢复后 sha `b8d96966f8181b34` ✅

**连锁效应（重要）**：W1-3 的判据③第二腿原断言「绕过闸直调 core ⇒ retired 确认被重置为 0」（用来证明它的闸不是装饰）。
我的修复**让该腿按设计变红并播报「core 已修」** —— W1-3 据此把它**升级为钉住目标不变式**（覆盖面更强，不是放宽）。这是判据有牙的正确表现。

### 3.2 跨席回归的修复派单

W1-2 翻转 JEV 缺省 ⇒ 打破 W1-3 写面内 2 条判据（该测试的 jev 挂载点未显式声明通道）。
我**A/B 独立确认归因**后派修，W1-3 按最小改动只改**受影响的 2 个挂载点**（另 2 个是刻意的反向腿，不动），
并**加了「显式通道自证」**（`assert status().channel === "ollama"`）——理由：显式声明本身不会被机检，若有人改回 `{}`，腿会静默重新依赖全局缺省。
