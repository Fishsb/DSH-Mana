## 5. 未决项

1. **⛔ core 生产检索真的在泄漏退休行（本批不敢动 core，故未修）** ——
   `packages/core/src/index.ts:526-534`（`recallLexical`）的 FTS SQL **没有 `AND retired=0`**。
   实测（真 temp 库 + 真 `core.writeMemoryItem` 写入 + 本席 `retireMemory` 置位）：
   ```
   core.recallLexical("开源免费") ids = ["alive","gone"]     ← gone 是 retired=1
      ==> retired=1 出现在 core 生产检索里的条数 = 1  【泄漏】
   long-term.searchLiveMemories  ids = ["alive"]
   ```
   ⇒ 目前 **A2-7 只在 long-term 侧成立**；走 core 那条检索面，「退休行不泄漏」**不成立**。
   `[建议决策] A2-7 的过滤腿要不要补进 core.recallLexical | 选项：(A) 主持人开 core 单席补 1 行 AND retired=0 并加机检 / (B) 把 core 检索面改走 long-term 的实现 | 推荐：(A) 理由：core 是契约真源且现成 SQL 一行之差，改面比改线小，且能立刻补一条"退休行不进 core 召回"的机检。`
2. **写口归属冲突（不影响本批，但会撞车）**：`packages/forgetting/src/archive.ts:224` 明文把
   「置 `retired` 且不删行」的写口归给 **core**，本席按派单实现在 **long-term**。
   ⇒ 若 S-forgetting 席照该行去等 core 的写口，会出现**两套写口**（派生量/写点分裂）。
   `[建议决策] retired 写口的唯一所有者 | 选项：(A) 认 long-term（改 forgetting 那行指向）/ (B) 认 core 写口、本批实现降级为参照 | 推荐：(A) 理由：本批已交付且带机检与负向对拍，而 core 侧目前无任何 retired 写原语；代价只是改 forgetting 一行字符串。`
3. **无审计行**：retire/restore 不写 `mana_trace` / `inject_log` ⇒ 「谁在何时退休了哪条」**事后不可查**。
   本批刻意不偷偷补（会改变本包"零行为"形态面），如实登记。
4. **并发读数口径**：`SoftDeleteOutcome` 的 `rowsBefore/rowsAfter` 是**诊断读数**，
   多写者并发时两者可能读到不同快照；「永不物理删除」的真保证来自**本模块不发 DELETE**这一构造事实
   （已在 `retirement.ts` 的 `mutateRetired` 注释里写明，未夸大）。
5. **机制哨兵的可能误报**：`probeFtsIndex` 腿断言"退休行仍在 FTS 索引里"。若将来 FTS 同步机制
   改成按 retired 剔除，该腿会红 —— **那是机制变更的信号，不是判据坏了**，注释里已写明处置顺序
   （先看机制、再决定过滤腿是否仍必要）。
