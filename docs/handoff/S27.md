### 1.1 `related_ids` 的格式（**本批首次定义**，下游按此读）

```json
[{"id":"m-a","w":0.03},{"id":"m-b","w":0.01}]
```

**三条选型理由（对着本仓已有事实，不是偏好）**：
1. **必须带权重**：该列是 `long-term/src/activation.ts:66` `associativeActivation` 的 `weight` 的**唯一来源**；
   只存 id 列表 = 把 L-03 的全部产出丢掉，下游只能填默认值（与「没实现」在数据上同形）。
2. **必须是数组而不是对象 map**：本机实测（Node v22.22.1）**整数样字符串键会被重排到最前** ——
   `JSON.stringify` 把 `{m2,"mem-b","123","7"}` 输出为 `{"7":0.04,"123":0.03,"m2":0.01,"mem-b":0.02}`。
   记忆 id 可能是数字串 ⇒ map 让「落库序」与「读回序」不可复算。数组**显式按 id 字典序**（`encodeRelated`）⇒ 同一组关系只有一个字节串。
3. **不用逗号分隔**：`tags` 用逗号是因为它无序；本列是 `{id → 权重}` 的映射，逗号分隔需要 `id:w` 微语法，
   而 id 含 `,`/`:` 时**解析歧义且无报错**（静默错位）。JSON 只需 `JSON.parse` 一处，非法输入**抛**而非错位。

**解析四态**（`NULL` / `''` / `ok` / `invalid`）**不得混同**；`invalid` 的 `items` **恒为 `[]`** 且带**非空 reason**
（`invalid` 绝不降级成「没有关系」——`catch { return null }` 的教科书形态，`docs/contract/degradation.md` 硬约定 1/2）。
