## 四、下一步方案（4 批，按「接线 → 扇出 → 驱动 → 规模」排序）

> **排序原则**：先接通（才有工作量）→ 再给生成能力（才有力气）→ 再上驱动者（才自动流）→ 最后规模。
> **每批都可独立验收**，且**都为下一批解除阻塞**。

### 批次 N1 · 接通四链（解除根因 A）★ 最高优先

**目标**：让巩固/再巩固/遗忘/学习**在生产侧有触发者**，把「实现完成」变成「系统能跑」。

| 子项 | 内容 | 写面 |
|---|---|---|
| N1-1 | **链驱动者**：在 `scheduler` 增加七链调度（按 V10 §18.2 触发时机表；无定时器 ⇒ 由宿主事件驱动） | `packages/scheduler/src/` |
| N1-2 | **Write Gate 接线**：`writeMemoryItem` 补生产调用方（`perception` → Write Gate → `long-term`） | `packages/long-term/src/` |
| N1-3 | **Recall Gate 接线**：`recallGate` 接进检索路径（当前零调用方 ⇒ 记 NONE） | `packages/vector/src/` |
| N1-4 | **事件消费者补齐**：`mana/recall` / `mana/injection` 的消费者 | 按链归属 |

**验收**：每链一条「**端到端真跑**」用例（造输入 ⇒ 该链产出可查行）——**判据不得只看单包单测**。
**反证**：卸载驱动者 ⇒ 该链不再产生新行。

### 批次 N2 · 建生成扇出层（解除根因 B，**吃掉 120 并发**）★★ 本方案的并发落点

**目标**：新建 **LLM 生成扇出层**，让「N 项生成任务」能并发跑满 API 的 120 并发。

**设计要点**（承接 JEV`JevGuard` 已验证的范式，**不另发明**）：

| 维度 | 设计 |
|---|---|
| **并发上限** | 可配 `maxConcurrency`，缺省 **32**，上限 **120**（吃满 API 能力） |
| **背压** | 队列 + 超时 + 显式降级（**照抄 `JevGuard.begin()` 的槽位移交语义**：`inFlight` 不变 ⇒ 无过订窗口） |
| **逐项归因** | **每项独立落痕**（成功/失败/降级各自可查）—— 不得因批量而丢单项归因 |
| **部分失败** | 一项失败**不得**中断整批（与 JEV 的 fail-closed 不同：生成是**可容忍部分失败**的） |
| **预算** | 每批次 token/次数预算 + 熔断（复用六护栏范式） |
| **幂等** | 每项带稳定幂等键 ⇒ 重试不产生重复行 |

**首批消费者**（正好是 §1.1 里 0 落点的 8 项能力）：

| 能力 | 归属链 | 扇出粒度 |
|---|---|---|
| 摘要与标签 | 编码 | 每条记忆 1 项 |
| 语义抽象 / 合并判断 | 巩固 | 每合并候选 1 项 |
| 压缩摘要 | 遗忘 | 每条归档 1 项 |
| 原则提炼 / 路径归纳 | 学习 | 每会话 1 项 |
| 深度睡眠归纳 | 巩固+学习 | 每批次 1 项 |

**验收**：真跑 **N=120 项** ⇒ 全部有落痕、无丢项、无重复、失败可指认；**实测吞吐**写入册面（作为首测基线）。
**反证**：把并发降到 1 ⇒ 耗时显著上升（证明并发真的在起作用）。

### 批次 N3 · 判定链「**批 × 扇出**」双级并发（解除根因 C）

**目标**：把 JEV 判定从「替身 + 串行 + 并发上限 4」改成「**真 JEV + 批 × 扇出**」。

> **⚠ 更正**：上一版写「扇出无效、只做批量」—— 那是**拿本地替身的读数**得出的，**已撤回**。
> 真 JEV 实测：**批量有效（50 问 1.75s）且并发有效（120/120 成功，p95 3.86s）** ⇒ **两者可叠加**。

| 子项 | 内容 | 依据 |
|---|---|---|
| **N3-0** ★ | **把真 JEV 打开**：`channel` 从缺省 `'ollama'`（替身）切到 `'systemone'`（`jev-1.13`）；凭据已在 `~/jev/.env` | 现状「配置与能力不匹配」：有真 JEV 却在跑替身 |
| N3-1 | **批**：一次请求塞 N 问（`questions` 是**以 id 为键的 map**，非数组 —— 我实测踩过，数组会 400） | 50 问 1.75s vs 单问 2.32s |
| N3-2 | **扇出**：并发 M 个请求；`maxConcurrency` 缺省从 **4** 提到可配（上限 120） | 120/120 成功，p95 3.86s |
| N3-3 | **两级叠加**：有效吞吐 = **N × M**（当前 N=1、M=4 ⇒ 有数量级余量） | 实测：10 问 × 120 并发 = 26.1 req/s |
| N3-4 | **逐问对位断言**：`answers` 是**以 id 为键的 map** ⇒ 天然对位；但**结果处理不得退化成按序数组**（替身通道才有「裸行无编号」问题） | 我实测真通道返回 `{"worth_keeping":{...}}`，键即 id |
| N3-5 | 批量路径降级：整体失败 ⇒ **逐项**降级留痕，不得整批静默 | 本仓既有纪律 |

**验收**：① 真 JEV 通道生效（`status().channel==='systemone'` 且落痕 `model: typesafe/jev-1.13-*`）；
② 50 问单请求 ≈1.7s；③ 120 并发 p95 < 5s、ok=120/120；④ **有效吞吐 ≥ 20 req/s**（当前替身串行远低于此）。
**反证**：把 `questions` 改成数组 ⇒ 必 400（我已实测）；把并发降 1 ⇒ 耗时显著上升。

## 七、诚实缺口（未验证，不得当 PASS）

- **DSH API 中转站的 120 并发的真实可用性未验证** —— 我实测的是 **`nano-gpt.com` 的真 JEV 通道**（120/120 成功），**不是 DSH API 中转站**（那是你说的、当前会话在用的那条链）。N2/N3 的验收里必须**首测** DSH API 那条；
- `dshapi` 侧并发/限流策略未核（配置里只有 `maxRetries: 20`，**无并发字段**）；
- `packages/llm` 是**纯转发层**（无重试、无缓存、无并发控制）⇒ N2 的扇出层要**自带**这些；
- **A0 门当前无读数**（`exit 4` 拒绝给结论）；
- 本方案**未评估**「生成质量」—— 8 项能力只有**通道**，质量需首测后自设基线。

---

> **一句话**：**并发不是瓶颈，管道才是。** 当前 7 条链有 4 条静止、LLM 生成层零消费；
> 因此方案顺序是 **接线（N1）→ 生成扇出吃 120 并发（N2）→ 判定改批量（N3）→ 规模（N4）**，
> 其中**只有 N2 吃 120 并发，N3 反而要减扇出**（实测：JEV 从 8 到 120 并发吞吐不变）。
